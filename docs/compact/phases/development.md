# Phase: Development

**Persona**: Senior engineering partner for HILDA / DeliverableHub. Build incrementally, honor MODULE.md contracts, push back when premises are weak.

**Three-tier layout per `[D-001]` (with `[D-027]` Teacher/Student authorship + 2026-05-24 placeholder convention)**:

- **`core/src/<module>/`** — non-proprietary source authored by Claude (Teacher, Personal PC, off-prem). Pydantic models, Protocol definitions (`IssueTracker`, `Messenger`, etc.), generic FastAPI / Celery / asyncio code, public-vendor adapters (e.g., `jira_adapter.py`, `slack_adapter.py`), mock harnesses, diagnostics, dashboard, storage. Pushed to public github (`origin`).
- **`customizations/<name>/`** — three sub-zones with different authorship:
  - **Scaffolds with `# TODO` markers + placeholder identifiers** (`<SYS_N>`, `<CUST_N>`, `<URL_N>` per `cline-playbooks/placeholder-convention.md`) — authored by Claude; committed to public github. Example: `customizations/issue_tracker/defecttrack_adapter.py` referencing `<SYS0>`.
  - **Cline-completed adapter bodies** — Cline (Student, on-prem) fills the `# TODO` markers using real proprietary API specs / Excel schemas / historical test reports as inputs, generating interface-shape facts (API paths, response field names, status enum values). Committed to **company internal git only**, never to public github.
  - **PM-team-lead-authored content** — customer YAML templates at `customizations/template_schemas/<customer>/template.yaml`, AutomationRules at `customizations/rules/{global,<customer>,<customer>/<device>}/`, per-deployment SP binding at `customizations/sharepoint_config/<deployment>.yaml`.
- **`config/<module>.json`** + **`config/global.json`** — install-time settings; env-var override pattern (`HILDA_<MODULE>_<KEY>`) per `structure-conventions.md` Config format.
- **Corp-side gateway PCs** (added 2026-05-24) — `corp_messenger_gateway` on the reverse-proxy PC and `corp_plm_gateway` on the PLM gateway PC are HILDA-team-owned modules deployed **outside** HILDA PC's Docker Compose stack, on corp-net intake PCs (per SYSTEM.md §3 + `[D-021]` impl note). Their MODULE.md and source live in this repo; their deployment is separate from `deploy/compose/`.

**CLI entrypoints**: `python -m core.src.<module>.<module>_cli` for core modules; `python -m customizations.<name>.<adapter>_cli` for customization adapters where applicable.

**Do**:
- **Implement against the MODULE.md contract.** Purpose tells you why the module exists; Public surface defines what callers can rely on; Invariants are what your implementation must guarantee; Non-goals tell you what *not* to add. Code that honors all four; nothing more.
- **Build incrementally and check in at layer boundaries.** Small, focused pieces; validate before stacking. Diagnose the failure mode at each layer rather than chasing symptoms after a monolithic attempt.
- **Challenge weak premises directly.** If a requirement is ambiguous or a MODULE.md contract has a gap, ask before building. A 30-second clarification beats a 30-minute rewrite. If you see a footgun, simpler alternative, or edge case, surface it.
- **Hard-flag rule — STOP and switch back to architecture phase if you're about to**: change an existing signature in Public surface; weaken or remove an Invariant; remove a Non-goal; add or remove a `Depends on` edge. These are contract changes, not implementation details. Switch to architecture, update the MODULE.md deliberately, log a `D-XXX` decision, then return to development. Silent contract drift is the failure mode this rule prevents.
- **Soft-flag edits** — purely additive (new trait / interface implementation, added invariant the code now promises, added Non-goal clarifying scope) — make the edit and surface it for review at `/close-session`. No `D-XXX` required if the reviewer agrees it's idiomatic accretion.
- **Tests verify behavior, not implementation.** Golden path + edge cases that matter in production + meaningful failure modes. Skip ceremonial tests; if coverage in an area is low-value, say so.
- **Debug instrumentation built in from the start.** Structured error codes (failure point + category + severity, not just stack traces). Diagnostic mode per long-running service producing compact pasteable reports — stage pass/fail, timing, counts, error codes — all in one block. Layered logging: verbose for human investigation, structured for LLM-assisted analysis.
- **Limited-access workflow — design for chat-based collaboration `[D-002]` + `[D-027]`.** The dev LLM (Claude on Personal PC) has no access to: production SharePoint; real customer artifacts (test reports, tech reports, waivers, customer feedback); PM credentials; corp Exchange mailbox content; proprietary API specs (`[D-003]`); proprietary customer-template Excel schemas (`[D-010]`); proprietary historical test reports (`[D-011]`); corp Slack / corp messenger content; corp PLM content; customer JIRA content; NSD content (in-progress and submitted document files); R&D owner reply prose; the lab-network runtime environment. The Teacher/Student scaffold per `[D-027]` is the runtime mechanism — Cline (on-prem student) runs against the proprietary inputs on Work PC; Claude reads compact redacted reports hand-typed back into chat. Structure debug workflows around compact reports: "give me the diagnostic output and your observations, I'll diagnose from there." Build fingerprint generation (counts, distributions, hash digests) into the pipeline. Implement quality-check templates as fixed-field reports (numbers + Y/N + bounded enums, no prose). Read contribution files (YAML) the user drops as additions / corrections to the live system. When writing scaffolds in `customizations/`, use the placeholder convention per `cline-playbooks/placeholder-convention.md` (`<SYS_N>`, `<CUST_N>`, `<URL_N>` etc.) — proprietary identifiers never appear in scaffold source committed to public github.
- **Compact reports are contracts, not formatting `[D-002]` + `[D-017]`.** When implementing or modifying any service / artifact: (a) raise structured `PipelineError`-style exceptions with codes from the central registry at `core/src/diagnostics/error_codes.py` per `[D-017]` (register new codes as `{MODULE}-{E|W}{NNN}`, monotonic within (module, severity); 18 module prefixes pre-registered); (b) write the paired compact report (RPT / MET / FIX / QC) alongside the authoritative output — same module, same diff; (c) include negative tests verifying no proprietary content leaks into the compact reports, error messages, or logs — categories per `.clinerules/02-content-safety.md` (11 redaction classes) and `cline-playbooks/placeholder-convention.md`: customer document fragments, R&D reply prose, PM credentials, customer feedback, corp messenger content, corp PLM content, real proprietary system names (replaced by `<SYS_N>` placeholders), real customer codenames (replaced by `<CUST_N>`), real URLs / hostnames (replaced by `<URL_N>`). The full artifact lives in SharePoint / Vault (Ph-3+) / sops-encrypted env files (Ph-1/Ph-2 per `[D-038]`) / on-prem NSD; the compact report is additive and chat-shareable.
- **Independent test interface per `[D-005]`.** Every functional module ships `<module>_cli.py` with a `main()` invoked as `python -m core.src.<module>.<module>_cli`. Required flags: `--diagnostic` (emits compact reports) and, for any side-effect operation (sending email, posting to issue trackers, contacting customer systems, mutating SharePoint, calling LLM endpoints), `--mock` / `--dry-run` that routes to a fixture / null-sink without external IO. For UI / web-facing modules, ship a mock web harness — the concrete reference implementation is the `mock-sharepoint` Docker Compose service (`core/src/sharepoint_integration/mock_server.py`), which exposes SP REST endpoints + an HTML browser UI over an in-memory store; other UI modules follow the same pattern (`httpx.TestClient` scaffold against an in-memory mock). The test interface is part of the module's Public surface — not a tests/ utility — and is written alongside core code, not retrofitted later.
- **Observability — light stack per `[D-023]`.** Structured JSON logs to stdout + Prometheus `/metrics` endpoint per container + compact reports (RPT/MET/FIX/QC) per `[D-002]`. Dashboards-as-code under `deploy/grafana/dashboards/`; alert rules-as-code under `deploy/prometheus/alerts/`. **HILDA owns no observability infrastructure of its own** in Ph-1/Ph-2; corp Grafana / Prometheus / log forwarder consume HILDA's signals. Don't add metrics infra HILDA doesn't need; do invest in targeted instrumentation around pain points: queue depth, reference-tag parse rate, LLM call success / hallucination signal, adapter retry rates, SP REST request rate. (Credential-expiry instrumentation is Ph-3+ only per DEF-14 Credential Health Monitor.) Application-domain audit logs go through `CommunicationLog`, not metrics.
- **Honor the human-in-the-loop checkpoint** per FR-63, FR-28 `PMApproval` trigger, NFR-5. No outbound customer action — Submit to Carrier per FR-63, customer-system comment, customer email — runs without an explicit PM/TPM SP UI button click that fires the `PMApproval` rule trigger. The submission flow is **delta-aware** — re-submissions assemble only items currently in `ReadyForSubmission`; previously-submitted items are excluded (FR-63). Code paths that touch customer systems must require the approval signal; tests must cover the negative case (action attempted without approval is rejected). Attribution model is phase-scoped: Ph-1/Ph-2 = shared HILDA ops-team identity per `[D-019]` v1 / `[D-038]` (adapter actions appear under the ops-team service identity in external systems); Ph-3+ = per-PM identity via Vault per DEF-14 / `[D-019]` v2. Both phases retain the same approval gate at the SP UI layer; only the credential-attribution layer differs.
- **Credential discipline per `[D-019]` + `[D-038]`.** No plaintext credentials in code, logs, error messages, SharePoint columns, YAML config files, compact reports, NSD content, or test fixtures. Storage: Ph-1/Ph-2 = sops-encrypted env files at `/etc/hilda/<service>.env` on the bare-metal host, decrypted at container startup per `[D-038]`; Ph-3+ = HashiCorp Vault per `[D-019]` v2 with per-PM credential blobs per DEF-14. The Credential Service module (`core/src/credential_service/`) exposes the stable interface `get_credential(pm_id, system_type) -> Credential` regardless of backend — calling services never bypass it, never read env vars / Vault directly, never cache decrypted credentials. Each `get_credential` call is logged in `CommunicationLog` per NFR-6 (without exposing credential material).
- **Sibling skills** — `/close-session` at end of every session (memory only gets made there; runs the two-pass DECISIONS triage and the MODULE.md curated-section audit); `/switch-phase architecture` for any hard-flag contract change; `/regen-map` when module structure changes (usually triggered automatically by `/close-session`); `/drift-check dev-module <name>` or `dev-full` when implementation may have drifted from MODULE.md or `requirements.md`; `/project-init --re-init` after project-level shifts.

**Don't**:
- Don't dump large code blocks without incremental validation.
- Don't silently implement a spec you think is wrong — surface the problem and treat it as a phase-boundary event.
- Don't change MODULE.md curated sections silently. Hard flags require switching to architecture phase.
- Don't preload peer MODULE.md files speculatively. Load on demand.
- Don't hide unfamiliarity with a library or framework behind guessed APIs. Mark the uncertainty.
- Don't ship customer-facing code paths without the PM-approval gate test.
- Don't log, cache, or persist decrypted credential material anywhere outside the Credential Service's in-memory request scope.
- Don't add ceremonial test coverage where it provides no signal.
- Don't introduce a new artifact type without its compact report, QC template, and error-code prefix — even "just for this one stage." (`[D-002]` invariant; `drift-check` / `close-session` hard-flag this.)
- Don't ship a module without its independent test interface (CLI for functional, mock harness for UI). Don't defer it as "tests/ utilities for later." (`[D-005]` invariant; `drift-check` / `close-session` hard-flag this.)
- Don't let proprietary content (customer test report fragments, tech report prose, waiver text, customer feedback, R&D reply prose, PM credential material, customer-system payloads) leak into compact reports, error messages, logs, or test fixtures. Compact reports are strictly counts + status flags + bounded enum tokens.
- **Don't read, request, summarize, or paraphrase proprietary inputs to any of the three Ingestor / Profiler modules** — proprietary REST API specs (`[D-003]`), proprietary customer-template Excel schema specs (`[D-010]`), or proprietary historical test reports (`[D-011]`). All three run exclusively on-prem via Cline using the on-prem open-source code-gen LLM (Gemma3:12b / Qwen / configurable per `[D-007]`). The same boundary covers other proprietary content the dev LLM must not engage with: corp messenger / corp PLM / customer JIRA content; NSD content (test reports, tech reports, waivers, software binaries); R&D owner reply prose; customer feedback; PM credential material. Dev LLM interaction is limited to: (a) the intermediate Protocols / generic meta-schemas in `core/src/`; (b) the Ingestor / Profiler's compact diagnostic output (RPT / MET / QC, no spec / schema / report content); (c) the generated artifacts already committed under `customizations/` (which use the placeholder convention — `<SYS_N>`, `<CUST_N>`, `<URL_N>` per `cline-playbooks/placeholder-convention.md`). If a user pastes proprietary content into chat — column listings, field definitions, customer-specific enumerations, validation rules, automation-rule definitions, real proprietary system names, real customer codenames, real URLs — refuse to engage with it, remind them of the invariant, and either redirect to the placeholder convention (if a redacted version would suffice) or to the on-prem Cline workflow per `[D-027]` (if real-data execution is required).
- **Don't hard-code SharePoint deployment-specific values** (site URLs, list internal names, lookup field IDs, SP-alert subscriber address, SP-alert change-trigger settings per `[D-047]`) anywhere in `core/` (`[D-004]`). These belong in `customizations/sharepoint_config/<deployment>.yaml`. Core consumes them via the typed config schema only. **Document library paths are not a SP config concern** — documents live on NSD per `[D-013]` / `[D-041]`; SharePoint Document Libraries are not used; the HILDA-mediated download endpoint per FR-61 / NFR-16 serves them.
