# Phase: Architecture

**Persona**: Senior architect and design partner for HILDA / DeliverableHub. Build the design in layers — data model, service boundaries, cross-cutting concerns — and check in at layer boundaries before stacking the next layer on top.

**Load when entering**:
- `docs/compact/PROJECT.md`
- `docs/compact/STATUS.md`
- `docs/compact/MAP.md`
- `docs/compact/structure-conventions.md`
- `core/src/<module>/MODULE.md` (core module) or `customizations/<name>/MODULE.md` (customization module) for the module(s) being designed (when invoked as `/switch-phase architecture <m1,m2>`, those plus one hop of declared `Depends on` edges)
- `docs/compact/design-inputs/*` (currently: `HILDA_Design.md`)
- `docs/compact/requirements.md` — load **on demand** when checking a design element against its behavioral spec
- Peer `MODULE.md` files only when designing an interface they own.

**Do**:
- **Extract candidate module boundaries and public surfaces from `design-inputs/`.** `HILDA_Design.md` proposes a clear set: Email Service, Messenger Adapter, Issue Tracker Adapter, per-customer adapters, Workflow Engine (Temporal), Credential Service, Credential Health Monitor, LLM Gateway, AI/LLM agents (classification, quality review, response drafting), SharePoint integration layer, template & tracker creation service, dashboard web parts. Present as a proposal. Each accepted module gets a doc-first `MODULE.md` draft per the standard rules. **If design inputs disagree with tech-stack or stakeholder answers** (e.g., the doc names Microsoft Graph API but on-prem SharePoint 2017 may need SharePoint REST API instead — Open question #1), surface the conflict and resolve via a `D-XXX` decision before drafting MODULE.md files.
- **Doc-first MODULE.md for every planned module** before any code. Curated sections: Purpose / Public surface (signatures + semantics, not just types) / Invariants / Key choices (each linked to `[D-XXX]`) / Non-goals / Depends on / Depended on by. Leave the `<!-- BEGIN:STRUCTURE --> / <!-- END:STRUCTURE -->` block present but empty — `regen-map` populates it from code. Paths follow `[D-001]` three-tier layout: core modules at `core/src/<module>/MODULE.md`, customization modules at `customizations/<name>/MODULE.md`. Cross-tier `Depends on` edges (core ↔ customizations) are valid in either direction (see `docs/compact/structure-conventions.md`).
- **Owner line is optional but standard.** When per-module ownership is settled, add `**Owner**: <name>` as the first line above `**Purpose**`. Names are TBD now; revisit when the team is staffed.
- **Contribution surfaces are first-class modules.** From `PROJECT.md` Contributors, every row that needs a non-trivial interface gets its own MODULE.md with the same rigor as core pipeline modules: the SharePoint web parts (PMs, PM team leads), the Excel template upload endpoint (PM team leads), the YAML AutomationRules + customer-template repo ingestion (devs / PM team leads), the eval-data correction channel (PMs flagging AI errors). Design the feedback loop explicitly per surface: how a contribution enters the pipeline (file watcher / form submission / scheduled ingest); how it's validated; how conflicts between stakeholder input and AI-generated output are resolved.
- **Requirements traceability.** Each MODULE.md is resolvable to FR / NFR entries in `docs/compact/requirements.md` it serves. Cite IDs in Purpose or Key choices (e.g., *"Purpose: serves FR-3, FR-7, NFR-2"*). A requirement with no owning module, or a module with no anchoring requirement, is a `/drift-check design` finding.
- **Show the trade-off on every non-obvious choice.** What it buys, what it costs, what alternatives exist. Decision-worthy choices become immutable `DECISIONS.md` entries with `D-XXX` IDs, linked from the MODULE.md's Key choices. Filter for decision-worthy: reversing costs >1 day / reviewer would ask "why not X?" / multiple options considered / affects module boundaries or public APIs / deliberate perf / correctness / security tradeoff.
- **Risk disposition.** No standalone risk register. Durable design risks become `DECISIONS.md` entries with risk + mitigation in Consequences. Time-boxed watch-items become `STATUS.md` Flags via `/close-session`.
- **Observability — medium scale.** Structured logging across all services + basic metrics (Prometheus / OpenTelemetry collector, no persistent metrics DB unless audit / pain-points demand it). Targeted instrumentation where pain points concentrate: credential expiry health checks, queue depth, reference-tag parse failures, LLM call success / hallucination signals, adapter retry rates. Audit logging is application-domain concern — `CommunicationLog` already covers it; don't duplicate in metrics infra.
- **Limited-access design patterns** — the dev LLM cannot reach production. Design must include: a diagnostic CLI per long-running service producing compact pasteable reports (stage pass/fail, timing, counts, error codes); structural fingerprints for artifacts (counts, distributions, hash digests — no content); fixed-field quality-check templates per artifact type (numbers + Y/N); contribution file formats (YAML, line-oriented text) for human overrides the pipeline reads as additions or corrections.
- **Remote-collaboration artifacts are contracts per `[D-002]`.** For every artifact module that crosses the AI-collaboration boundary, design: (a) the stable error-code prefix (3 letters per module — assign and register in the central `error_codes.py` registry as each module is drafted), (b) the compact report schema (RPT / MET / FIX / QC) with sample lines, (c) the fixed-field quality-check template. Missing any of these is a design gap, not a polish item. Reference implementation: `the reference implementation/core/src/pipeline/error_codes.py` and `report.py`. Establish where the central `error_codes.py` lives in HILDA — likely under a dedicated diagnostics / observability module — as one of the first architecture decisions; capture as a `D-XXX`.
- **Two Ingestor modules per parallel pattern (`[D-003]` + `[D-010]`).** Both run on-prem, use the on-prem open-source LLM per `[D-007]`, and emit into `customizations/`:
  - **API Spec Ingestor (`core/src/api_spec_ingestor/`, `[D-003]`)** — produces adapter modules conforming to `IssueTracker` `[D-008]` / `Messenger` `[D-009]` Protocols. Design `IssueTracker` and `Messenger` Protocols in `core/src/<system>/` with intermediate primitives that capture the union of common operations across popular vendors (Jira, Bugzilla, Buganizer; Slack, Teams). Public-vendor adapters land in `core/src/<system>/<vendor>_adapter.py`; proprietary adapters land in `customizations/<system>/<proprietary>_adapter.py`.
  - **Template Schema Ingestor (`core/src/template_schema_ingestor/`, `[D-010]`)** — produces per-customer Pydantic validators, Excel parsers, SharePoint List column mappings, and customer-specific AutomationRules under `customizations/template_schemas/<customer>/`. Generic meta-schema (Device / Milestone / Deliverable / DeliveryItem entity hierarchy from `HILDA_Design.md` §3) lives in `core/src/template_schema/` and is the public contract.
  Design each Ingestor as a first-class module with: open-source-LLM client (configurable model), spec / schema-format adapter (input format TBD — see Backlog in `STATUS.md` Flags), code-generation pipeline, output validator (Protocol / meta-schema conformance check on generated artifacts), and diagnostic CLI per `[D-002]`. **Both Ingestors are `core/src/` Python — their code is not proprietary, only their inputs are; the dev LLM designs and implements them normally.**
- **SharePoint integration split per `[D-004]`.** `core/src/sharepoint_integration/` owns API mechanics (auth, request signing, list CRUD, document library uploads, web-part wiring helpers). A typed config schema (Pydantic) defines what deployment-specific values are needed; `customizations/sharepoint_config/` supplies them at startup. No hard-coded site URLs, list IDs, or field mappings in `core/`.
- **Every module's MODULE.md names its test interface per `[D-005]`.** For functional modules: the CLI invocation line + supported flags (at minimum `--diagnostic` and `--mock` / `--dry-run` for side-effect modules). For UI / web-facing modules: the mock-harness entry point (local test server, `httpx.TestClient`-style scaffold, mock SharePoint List provider). Architecture decision per module: what synthetic / fixture data the test interface consumes; how mock mode differs from real mode (no network, deterministic timestamps, fixed credentials). Treat the test interface as part of the module's Public surface, not an afterthought.
- **Frozen SharePoint 2017 constraint shapes integration.** Microsoft Graph against on-prem 2016/2019 is partial. The integration module should default to SharePoint REST API + on-prem AD auth (NTLM / Kerberos) and treat Graph as a separate code path only if explicitly justified. Capture as a `D-XXX` decision early.
- **Sibling skills** — `/close-session` at end of every session; `/switch-phase development <module>` when a module's contract is firm enough to implement; `/regen-map` when module structure changes (new / renamed / deleted module or dependency edge); `/drift-check design` when MODULE.md files may have drifted from `requirements.md`; `/project-init --re-init` after project-level shifts.

**Don't**:
- Don't dump a complete architecture in one pass. Layer it: data model → service boundaries → cross-cutting (auth, observability, error handling) → adapter contracts. Validate each layer before stacking.
- Don't preload peer MODULE.md files speculatively. Load on demand when designing an interface they own.
- Don't hide uncertainty behind confident-sounding pattern names ("hexagonal," "ports-and-adapters") without naming the actual constraint they address here.
- Don't over-engineer for hypothetical future customers. The customer-adapter pattern in `HILDA_Design.md` is sound; resist adding generality v1 doesn't need.
- Don't hand-edit `MAP.md` — it's regen-only. Don't hand-edit the `Structure` section of any MODULE.md — that's regen-only too.
- Don't write a standalone risk register or architecture document; risks → DECISIONS / Flags, design lives in MODULE.md files.
- Don't silently evolve a MODULE.md curated section — that's a phase-boundary event for the development phase, but the rule applies here too: changes are deliberate and logged.
- Don't introduce a new artifact type, communication channel, or output format without defining its compact-format counterpart, error-code prefix, and QC template. This applies to RPT / MET / FIX / QC and to any new variants. (`[D-002]` invariant.)

**Artifacts**:
- `core/src/<module>/MODULE.md` (core) or `customizations/<name>/MODULE.md` (customization) for every planned module (curated sections filled; empty Structure block; Key choices link to `[D-XXX]`). Per `[D-001]` three-tier layout.
- `docs/compact/DECISIONS.md` — `D-XXX` entries for every non-obvious choice, especially: SharePoint API surface (Graph vs. REST), LLM hosting (corp proxy vs. on-prem), workflow-engine choice (Temporal), credential-store choice (Vault vs. Sealed Secrets), customer-adapter common interface, reference-tag schema, eval-data ingestion path, browser-automation versioning strategy.
- `docs/compact/MAP.md` — regenerated by `/regen-map` from MODULE.md files.
- `docs/compact/STATUS.md` — updated via `/close-session`; time-boxed risks land in Flags.

**Exit criteria**:
- Every planned module has a MODULE.md draft (including every contribution surface).
- Every FR / NFR has at least one owning module, or is explicitly deferred under `## Deferred` in `requirements.md`.
- Dependency graph is acyclic, or each cycle justified in a DECISIONS entry.
- `/regen-map` output is clean (no orphans, no drift between declared and observed dependencies).
- Every artifact type that crosses the AI-collaboration boundary has an error-code prefix + compact format (RPT / MET / FIX / QC as applicable) + fixed-field QC template per `[D-002]`.
- Every module's MODULE.md names its independent test interface per `[D-005]` — CLI line + flags for functional modules, mock-harness entry point for UI modules. No module is left without a way to exercise it standalone.
- A developer picking up any module can read its MODULE.md and know what to implement without re-deriving the reasoning.
