- **Observability — light stack per `[D-023]`.** HILDA owns and operates **no observability infrastructure of its own**; it emits standard signals that corp infra consumes. Structured JSON logs to stdout + Prometheus `/metrics` endpoint per container + compact reports (RPT/MET/FIX/QC) per `[D-002]`. Dashboards-as-code under `deploy/grafana/dashboards/`; alert rules-as-code under `deploy/prometheus/alerts/`. No HILDA-owned Grafana / Loki / Tempo / OTel collector / distributed tracing. Targeted instrumentation where pain points concentrate: credential expiry health checks (Ph-3+ only per DEF-14), queue depth, reference-tag parse failures, LLM call success / hallucination signals, adapter retry rates. Audit logging is an application-domain concern — `CommunicationLog` covers it; don't duplicate in metrics infra.
- **Limited-access design patterns** — the dev LLM cannot reach production. Design must include: a diagnostic CLI per long-running service producing compact pasteable reports (stage pass/fail, timing, counts, error codes); structural fingerprints for artifacts (counts, distributions, hash digests — no content); fixed-field quality-check templates per artifact type (numbers + Y/N); contribution file formats (YAML, line-oriented text) for human overrides the pipeline reads as additions or corrections. The full picture: the **Teacher / Student LLM scaffold per `[D-027]`** (Claude on Personal PC designs + commits scaffolds; Cline on Work PC executes against real proprietary inputs and pushes only to corp git; one-way air-gap), the **placeholder convention** at `cline-playbooks/placeholder-convention.md` (`<SYS_N>`, `<CUST_N>`, `<URL_N>` etc. — proprietary identifiers never appear in scaffolds committed to public github), and the **two corp-side intake PCs** (reverse-proxy PC + PLM gateway PC per SYSTEM.md §3) which expand the limited-access surface from "HILDA PC vs production" to a multi-host topology with explicit ownership boundaries.
- **Remote-collaboration artifacts are contracts per `[D-002]` + `[D-027]`.** For every artifact module that crosses the AI-collaboration boundary, design: (a) the **stable error-code prefix** (3 letters per module — assigned and registered in the central `core/src/diagnostics/error_codes.py` registry per `[D-017]` as each module is drafted; 18 module prefixes pre-registered there), (b) the **compact report schema** (RPT / MET / FIX / QC) with sample lines, (c) the **fixed-field quality-check template**, (d) any **proprietary-identifier placeholders** following `cline-playbooks/placeholder-convention.md` (scaffolds use `<SYS_N>` / `<CUST_N>` / `<URL_N>` with a registry comment block at the top of the file). Missing any of these is a design gap, not a polish item. Reference implementation: `the reference implementation/core/src/pipeline/error_codes.py` and `report.py`.
- **Three Ingestor / Profiler modules per parallel pattern (`[D-003]` + `[D-010]` + `[D-011]`).** All three run on-prem, use the on-prem open-source LLM per `[D-007]`, and emit into `customizations/`:

Public-vendor adapters land in `core/src/<system>/<vendor>_adapter.py` (v1 targets: customer JIRA per FR-25 and Slack per `[D-016]`); proprietary adapters land in `customizations/<system>/<proprietary>_adapter.py` (v1 targets: corp PLM via the Ingestor per `[D-003]` impl note 2026-05-14 and the proprietary internal messenger per `[D-016]`). Input format = OpenAPI 3.x canonical with preprocessing pass per `[D-015]`.
  - **Template Schema Ingestor (`core/src/template_schema_ingestor/`, `[D-010]` + `[D-018]`)** — produces per-customer Pydantic validators, Excel parsers, SharePoint List column mappings, and customer-specific AutomationRules under `customizations/template_schemas/<customer>/`.   Design each Ingestor / Profiler as a first-class module with: open-source-LLM client (configurable model), spec / schema-format adapter, code-generation pipeline, output validator (Protocol / meta-schema conformance check on generated artifacts), and diagnostic CLI per `[D-002]`. **All three are `core/src/` Python — their code is not proprietary, only their inputs are; the dev LLM designs and implements them normally; Cline runs them on Work PC against the real proprietary inputs.**

**Don't**:
- Don't dump a complete architecture in one pass. Layer it: data model → service boundaries → cross-cutting (auth, observability, error handling) → adapter contracts. Validate each layer before stacking.
- Don't preload peer MODULE.md files speculatively. Load on demand when designing an interface they own.
- Don't hide uncertainty behind confident-sounding pattern names ("hexagonal," "ports-and-adapters") without naming the actual constraint they address here.
- Don't over-engineer for hypothetical future customers. The customer-adapter pattern in `HILDA_Design.md` is sound; resist adding generality v1 doesn't need.
- Don't hand-edit `MAP.md` — it's regen-only. Don't hand-edit the `Structure` section of any MODULE.md — that's regen-only too.
- Don't write a standalone risk register or architecture document; risks → DECISIONS / Flags, design lives in MODULE.md files.
- Don't silently evolve a MODULE.md curated section — that's a phase-boundary event for the development phase, but the rule applies here too: changes are deliberate and logged.
- Don't introduce a new artifact type, communication channel, or output format without defining its compact-format counterpart, error-code prefix, and QC template. This applies to RPT / MET / FIX / QC and to any new variants. (`[D-002]` invariant.)

**Exit criteria**:
- Every planned module has a MODULE.md draft (including every contribution surface).
- Every FR / NFR has at least one owning module, or is explicitly deferred under `## Deferred` in `requirements.md`.
- Dependency graph is acyclic, or each cycle justified in a DECISIONS entry.
- `/regen-map` output is clean (no orphans, no drift between declared and observed dependencies).
- Every artifact type that crosses the AI-collaboration boundary has an error-code prefix + compact format (RPT / MET / FIX / QC as applicable) + fixed-field QC template per `[D-002]`.
- Every module's MODULE.md names its independent test interface per `[D-005]` — CLI line + flags for functional modules, mock-harness entry point for UI modules. No module is left without a way to exercise it standalone.
- A developer picking up any module can read its MODULE.md and know what to implement without re-deriving the reasoning.
