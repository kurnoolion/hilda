## Functional

### Tracker lifecycle & data model

- **FR-1** `[Ph-1]` — System creates a device tracker from one of three inputs: (a) a customer template `[Ph-1]`, (b) an Excel import conforming to the per-customer schema `[Ph-2]` (deferred alongside DEF-15 — requires Template Schema Ingestor), or (c) manual entry `[Ph-2]`.
- **FR-2** `[Ph-1]` — Tracker creation auto-populates the full Milestone → DeliveryItem hierarchy from the template, with all static fields pre-populated per `HILDA_Design.md` §3.3; DeliveryItems are grouped within a milestone by `tg_name` (anchors `[D-028]`); `plm_id` is not set at tracker creation — it is assigned per (owner × milestone) at collection kickoff (FR-8); each DeliveryItem's `expected_completion_date` is set at tracker creation to the parent `Milestone.target_date` and can be overridden per-item by the PM post-creation (FR-14); `doc_count` is pre-populated from the template per item; specifies how many `test_report` documents must be received before the item can advance to `OwnerClosed` — gates two transitions per FR-7: (a) immediate advance to `DocumentReceived` (intermediate state) once the count is reached via document arrival; (b) guard condition (1) of the `OwnerClosed` transition triggered by owner "done" confirmation; each TG group's `tg_owner` (the TG coordinator who knows current engineer assignments for that group — distinct from `owner`, the delivery engineer per item) is pre-populated from the customer template per `tg_name` group and applied identically to all items sharing that `tg_name`; TPM can override `tg_owner` per TG group in the SP UI before the Owner Discovery Function fires `[Ph-2]` (FR-71); each item's `email_cc_list` is pre-populated from the customer template's per-TG `default_cc_list` at tracker creation and can be overridden per-item by TPM via FR-14; each TG group's `email_group_alias` (optional; the TG's corporate email distribution list alias — e.g. `ims.corp@corp.com`; when set, all email outreach for items in this TG is sent to this alias instead of individual owner emails; the `owner` field on each DeliveryItem is still maintained and used for PLM issue creation and NSD path construction, but is bypassed for email outreach; TPM owner overrides via FR-14 are stored but have no effect on email routing when alias is set) is pre-populated from the customer template per `tg_name` group; each TG group's `corp_id_list` (optional; complete list of corp IDs for all TG members — item owners, `tg_owner`, and any other TG stakeholders; when set, used for all corp messenger outreach for this TG instead of individual owner corp IDs) is pre-populated from the customer template per `tg_name` group; each DeliveryItem's `review_required` (boolean; default `false`) is pre-populated from the customer template per item — when `true`, HILDA triggers LLM quality review (FR-53) on every received document for that item; when `false`, LLM review is skipped, `review_status` is set to `not_required`, `llm_review_findings` remains null, and the `OwnerClosed` guard condition (2) is vacuously satisfied; `item_type = Confirmation` items are always `review_required = false` and this field is non-editable for Confirmation items.
- **FR-3** `[Ph-1]` — PM can add, remove, or reassign DeliveryItems after instantiation without re-creating the tracker.
- ~~**FR-4**~~ — *(deferred 2026-05-12 → DEF-15: Excel import schema validation — implementation phase TBD)*
- **FR-5** `[Ph-1]` — Hierarchical data is enforced as Devices/Milestones/DeliveryItems with uniqueness on (device_id, milestone_name), (milestone_id, item_name), and (milestone_id, item_no); no Deliverable intermediate level (anchors `[D-028]`); all DeliveryItems with the same (milestone_id, owner) share the same `plm_id` — the PLM issue is one per (owner × milestone), not per item (anchors `[D-035]`).
- **FR-6** `[Ph-1]` — Milestone status and `milestone_completion_pct` are computed from the states of their child DeliveryItems.
- **FR-7** `[Ph-1]` — Item types, tracking modalities, customer delivery modalities, `delivery_state` values, and `doc_count` are extensible via configuration without code change; `doc_count` is a per-DeliveryItem integer from the template (default 1) specifying how many `test_report` documents must be received before the item can advance to `OwnerClosed` — gates two transitions: (a) immediate advance to `DocumentReceived` (intermediate state) once the count is reached via document arrival; (b) guard condition (1) of the `OwnerClosed` transition triggered by owner "done" confirmation; applies only to artifact item types; `Confirmation` items have `doc_count = 0`; `item_completion_pct` is a per-DeliveryItem computed field representing the document-review completion percentage across all received documents (see FR-70); `tracking_modality` is a **multi-value field** (list) per DeliveryItem supporting the following values — `Email` `[Ph-1]` (status + documents via email reply), `CorporateMessenger` `[Ph-2]` (status only; no attachments; not document-capable), `CorporatePLM` `[Ph-1]` (documents only; not status-capable; owner uploads to PLM directly; HILDA polls PLM, downloads, and writes the document file to `<doc_type_slug>/<doc_id_slug>/rev1/`; document arrival advances item to `DocumentReceived` intermediate state — does **not** set `OwnerClosed`), `NetworkSharedDrive` `[Ph-1]` (documents only; not status-capable; owner drops in shared drive `inbound/` folder; HILDA polls; document arrival advances item to `DocumentReceived` intermediate state — does **not** set `OwnerClosed`), `CustomerJIRA` `[Ph-1]` (status only; not document-capable; HILDA polls customer JIRA API for waiver/issue closure status; no outbound; no attachments); valid combinations require at least one status-capable modality (`[Ph-1]` `Email` or `CustomerJIRA`; `[Ph-2]` `CorporateMessenger` added) and at least one document-capable modality (`Email`, `CorporatePLM`, or `NetworkSharedDrive`) for items with artifact deliverables; `CorporateMessenger` escalation (FR-10) is automatic regardless of modality and is not a modality value itself; `OwnerClosed` transition is triggered when the owner explicitly confirms "done" via a status-capable modality (`Email` `[Ph-1]` or `CorporateMessenger` `[Ph-2]`) — the "done" confirmation is the **trigger** that evaluates the following two guard conditions, not a third condition itself: (1) `doc_count` reached (test-report count equals `doc_count`); (2) LLM review condition — vacuously satisfied when `review_required = false` for this item (no review triggered, no `AIReviewResult` awaited, item advances to `OwnerClosed` once condition (1) is met); when `review_required = true`: all received documents and all their revisions have been reviewed — for `test_report` documents: rule-based parser result (FR-16) AND non-null `llm_review_findings` (FR-53) present for every `rev_number` row in the document index; for `tech_report` and `waiver` documents: non-null `llm_review_findings` (FR-53) for every revision; if owner confirms "done" before condition (1) is met, HILDA sends a corp messenger notification informing the owner that documents are still expected — `delivery_state` remains `DocumentReceived`, no owner response is processed; if owner confirms "done" before condition (2) is met and `review_required = true`, state advance is deferred until all reviews complete; document receipt alone via `Email` attachment, `CorporatePLM`, or `NetworkSharedDrive` advances to `DocumentReceived` only — explicit owner "done" confirmation is always required to trigger guard evaluation; `[Ph-2]` owner may self-close directly in the SharePoint UI (FR-56); **`OwnerClosed` is a transient state** — items spend zero observable time there. On entry: (a) `actual_completion_date` is auto-set to today (immutable thereafter per FR-15); (b) HILDA immediately advances the item out of `OwnerClosed` via one of two forks. **Ph-1 (single-revision)** — only `rev1` exists for each document → `is_final = true` auto-set on `rev1` → item advances directly to `UnderPMReview`. **Ph-2 (multi-revision)** — if multiple revisions exist for any `doc_id_slug` → `TriggerVersionSelection` fires (FR-66) → owner selects the final revision via corp messenger → `is_final = true` set on selected revision → item advances to `UnderPMReview` after all selections are confirmed; `delivery_state` enumeration: `Open` (initial, set at tracker creation), `OutreachSent` (initial outreach dispatched per FR-9), `DocumentReceived` (document arrived via any ingest channel per FR-28), `UnderPMReview` (active TPM review gate: `OwnerClosed` transient fork lands here once `is_final` is resolved per the fork logic above; TPM reviews document findings in the SP UI per FR-56; TPM may override `is_final` to select a different revision `[Ph-2]`; explicit TPM approval via the per-item **Approve** action (`PMApproval` trigger, FR-28) advances the item to `ReadyForSubmission`), `OwnerClosed` (owner confirmed done via status-capable modality; `actual_completion_date` auto-set to today's date on this transition — not overwritten by subsequent state changes), `Delayed` (owner-reported delay — set via status modality, any pre-approval state), `Blocked` (owner-reported blocker — set via status modality, any pre-approval state), `ReadyForSubmission` (PM approved per FR-28 `PMApproval` trigger), `SubmittedToCustomer` `[Ph-1]` (submission package dispatched to customer per FR-18), `Closed` (reached by one of three paths: (i) PM/TPM manual override per FR-14 once carrier acceptance is confirmed; (ii) bulk Close All Items via FR-64; (iii) **TPM-Mark-Closed manual path for items with `no_customer_upload = true`** per FR-80 — TPM clicks "Mark Closed" in SP UI after standard `OwnerClosed` guards are met; HILDA enforces guards at click time, no bypass; DEF-20 carve-out applies to this specific manual path only; other automated transitions remain deferred per DEF-20); `Delayed` and `Blocked` are transient — PM or owner can move the item back to the prior active state; `Confirmation` items (`item_type = Confirmation`) skip both `DocumentReceived` and `OwnerClosed` entirely — owner "done" confirmation from `OutreachSent` advances directly to `UnderPMReview` (no document received, no FR-53 review, no `is_final` fork; `actual_completion_date` auto-set to today on this transition per FR-15-extended semantics); the PM Review section in SP UI for a Confirmation item shows no document list — surfaces only the owner's "done" confirmation timestamp + a TPM **Approve** action which advances to `ReadyForSubmission` via `PMApproval` trigger; `CustomerJIRA` items reach `OwnerClosed` via HILDA detecting JIRA closure (no owner message required); **`item_type` enumeration is 4-valued** (revised per `[D-053]` impl note 2026-06-08, supersedes the prior multi-valued enum): `Confirmation` (no documents — Yes/No reply only), `TEST_TECH_WAIVER_REPORT` (receives any of `{test_report, tech_report, waiver}`; `review_required = true`), `COMPLIANCE_CERTIFICATION_RELEASE_NOTES` (receives `compliance_certification_release_notes` documents; `review_required = false`), `Default` (auto-instantiated default work-item per milestone per FR-78; receives any document whose target work-item is not resolved). **`doc_type` enumeration is 5-valued**: `test_report`, `tech_report`, `waiver`, `compliance_certification_release_notes`, `unresolved`. **`doc_type` is NOT derived from `item.item_type`** (supersedes the prior 1:1 derivation framing per `[D-053]` impl note 2026-05-28b — withdrawn) — it is classified per inbound document via the FR-85 classification pipeline (filename regex + LLM for `{test_report, tech_report, waiver}`; `compliance_certification_release_notes` detected by filename regex only; `unresolved` on classification fail). **Alignment invariant** (anchors `[D-053]` impl note 2026-06-08): `TEST_TECH_WAIVER_REPORT` items hold doc_type ∈ `{test_report, tech_report, waiver}`; `COMPLIANCE_CERTIFICATION_RELEASE_NOTES` items hold doc_type = `compliance_certification_release_notes`; `Default` items hold any of the 5; mismatched (item_type, doc_type) pairs at ingest land on the `staged-not-classified` NSD path per FR-86 for TPM SP UI resolution per FR-87. `doc_type` is used as folder organiser `<doc_type_slug>/` on shared drive (when set) and as document index key. Downstream triggering: `test_report` → FR-16 parser always + FR-53 LLM review when `review_required = true`; `tech_report` / `waiver` → FR-53 LLM review when `review_required = true`; `compliance_certification_release_notes` / `unresolved` → no parser, no review (FR-16, FR-46, FR-53 do NOT fire). **`doc_count` counts `test_report` documents only** (intentional; if owner submits only waiver or tech_report, state remains in `DocumentReceived` and does not advance to `OwnerClosed` until a test_report arrives. **Template author guidance**: if the deliverable is satisfied without a test_report (waiver-only or tech_report-only cases), set `doc_count = 0` on the work-item — owner-done confirmation then advances state via the vacuous-guard path; the received document(s) are stored and reviewable but not required by the gating mechanism. Splitting into separate work-items does not help — all actionable items share the `TEST_TECH_WAIVER_REPORT` item_type and the same test_report-only doc_count semantic).

### Collection kickoff & ongoing tracking

- **FR-8** `[Ph-1]` — PM or TPM clicks **Start Collection** from the SharePoint milestone view (FR-56), sending one request to HILDA for the entire milestone; HILDA creates one PLM issue per unique (owner × milestone) pair via the IssueTracker adapter and writes the resulting `plm_id` to all DeliveryItems for that (owner, milestone) — this is a batch operation across the whole milestone, not per item; after PLM issue creation, HILDA fires FR-9 initial outreach for all open DeliveryItems in the milestone, advancing them to `OutreachSent`; PLM issue creation is idempotent — re-triggering Start Collection does not create duplicate issues for pairs that already have a `plm_id`; for items added to the milestone after Start Collection has already fired, per-item `StartItemCollection` logic applies (FR-28 `ItemCreated` trigger, FR-29).
- **FR-9** `[Ph-1]` — Initial owner outreach is sent via the DeliveryItem's `tracking_modality` (see FR-7 for all values); for `Email` modality: **(a) when `email_group_alias` is set for the TG** — one outreach email is sent to the alias containing all items in the TG grouped by owner; the email contains one structured BATCH reply block per owner (each block carries its own `BATCH-<id>`), so any TG member can fill in any owner's block and HILDA routes the response by the `BATCH-<id>` in the filled block; sender identity does not restrict which block a respondent may fill in; **(b) when `email_group_alias` is not set** — multiple DeliveryItems owned by the same recipient are consolidated into one outbound message per round identified by a stable `BATCH-<id>`, with a per-item structured reply block grouped by `tg_name` `[Ph-1]` and per-item `mailto:` quick-update tap-links `[Ph-2]` in the body; the outbound email populates the CC field with the union of `email_cc_list` values across all items in the batch (pre-populated from the template's per-TG `default_cc_list` at tracker creation per FR-2; overridable per-item by TPM via FR-14); CC recipients receive the full outbound email for visibility — their inbound replies are processed by FR-12 sender-mismatch logic (CC address is not the registered `owner` for the BATCH-id) and surfaced as a `Sender mismatch` flag on the PM dashboard for PM review; for `CorporateMessenger` modality, no initial outreach message is sent — CorporateMessenger is used exclusively as an escalation channel per FR-10 when email reminders yield no owner response; for `CorporatePLM` and `NetworkSharedDrive` modalities, outreach informs the owner of the expected delivery path (PLM issue reference or shared drive path) — outbound format TBD architecture phase; for `CustomerJIRA` modality, no HILDA-initiated outreach (HILDA polls the customer JIRA passively); on dispatch, all outreached DeliveryItems advance to `OutreachSent` delivery state.
- **FR-10** `[Ph-1]` — Rule engine sends scheduled reminders to owners when `delivery_state = "Open"` and `days_since_last_contact > N` (N is per-rule configurable); if email reminders yield no owner response for a further configurable period (no `last_updated` change after reminder_count ≥ M), the rule engine additionally sends a cross-channel escalation via corp messenger `[Ph-1]` (outbound only — inbound messenger responses handled by FR-54); when `corp_id_list` is set for the owner's TG, the escalation message is sent to all corp IDs in `corp_id_list` instead of the individual owner's corp ID; when `corp_id_list` is not set, the escalation goes to the individual owner's corp ID; if the owner has multiple open items in the same milestone, the messenger escalation aggregates all open items into a single message to minimise transactions.
- **FR-11** `[Ph-1]` — Rule engine escalates to owner + PM when `expected_completion_date - today ≤ N` and item is not Closed; `expected_completion_date` is set at tracker creation from the parent `Milestone.target_date` (FR-2) and may be overridden per-item by the PM (FR-14).
- **FR-12** `[Ph-1]` — Inbound email replies route to the correct DeliveryItems via three convergent paths, all keyed on the `BATCH-<id>`: (a) `[Ph-1]` a structured reply block edited in place by the owner, regex-parsed from the body; (b) `[Ph-2]` per-item `mailto:` tap-links that pre-compose tiny emails parsed from the subject (`[HILDA] BATCH-<id> ITEM-<n> <STATUS>`); (c) `[Ph-1]` free-text replies that match neither path are processed in two stages — (1) rule-based parsing attempts to extract status and comment against item-name tokens and `BATCH-<id>` context; above threshold, auto-apply and notify PM; (2) if rule-based parsing fails, the runtime LLM infers item classification and status — above LLM confidence threshold, auto-apply; below threshold, record as comments on all batch items and surface as a Manual triage flag on the PM dashboard (DEF-1 promoted 2026-05-13); when path (c) fires on an email that also contains attachments, a single fused LLM call processes email body, first-page attachment excerpts, and the batch DeliveryItem list together, covering both message classification and attachment routing in one pass (see FR-52, anchors `[D-034]`). Status applies are idempotent on `(BATCH-id, item-index, status)`; outbound is sent multipart/alternative and the structured block is ASCII-only; inbound email attachments are routed to DeliveryItems per FR-52. The sender email address is captured in `CommunicationLog` for attribution on every inbound path; if the sender matches the `email_group_alias` registered for the TG of the BATCH-id, no sender-mismatch flag is raised — the response is treated as an official TG response; if the sender does not match the registered owner email for the BATCH-id and does not match the TG's `email_group_alias`, the update is applied and a `Sender mismatch` note is surfaced on the PM dashboard for PM review (not a hard rejection); stricter sender-enforcement rules are configurable via `AutomationRules`.
- **FR-13** `[Ph-1]` — HILDA manages owner deliverables and internal artifacts across a **dual NSD topology** (anchors `[D-013]` impl note 2026-05-28): **NSD1** (bidirectional — hosts HILDA `internal/` tree at `\\NSD1\internal\<carrier>\<device>\<milestone>\<tg_name_slug>\` AND is one of the two ingress drives at `\\NSD1\<carrier>\<device>\<milestone>\<Folder-N>\`); **NSD2** (ingress-only at `\\NSD2\<carrier>\<device>\<milestone>\<Folder-N>\`; HILDA never writes to NSD2; NSD2 originals stay forever, no archival). Both NSDs SMB-mounted on HILDA PC; both authenticate via the same `hilda-svc` Kerberos keytab; both polled identically per the same `polling_schedule` AutomationRule (per FR-55). NSD2-sourced documents are classified into NSD1's `internal/` tree (cross-drive write). **Owner inbound flat folder structure** — owners drop documents at `\\NSD_X\<carrier>\<device>\<milestone>\<Folder-N>\...` (no per-item folders — items have varying counts and per-item folders were rejected by owners with 40+ items). Folder names are TG-assigned (not item-assigned); item identification at HILDA-side via FR-52's 5-step pipeline (substring on tags → fuzzy on item_name → folder template if TG opted in → LLM → staged → default work-item). **HILDA internal tree path conventions** — under `\\NSD1\internal\<carrier>\<device>\<milestone>\<tg_name_slug>\`, four areas at TG level: **(1) `_zip_audit/<original_zip_filename>.zip`** — archive of received zip; **(1a) `_zip_audit/<original_zip_filename>/<extracted-tree>/`** — extracted contents co-located with the zip (audit-only; never uploaded to PLM or carrier portal); **(2) `<item_slug>/<doc_type_slug>/<doc_id_slug>/revN/<original_filename>`** — classified storage per item (post-FR-52 routing); `doc_id_slug` derived by slugifying the first-received filename, stable across revisions; `rev1/` = initial receipt; `revN/` (N ≥ 2) = subsequent revisions per FR-17; `[Ph-2]` `is_final = true` set on TPM-approved revision per FR-66; `download_url` = HILDA-mediated link (`https://hilda.corp/dl/<scoped_token>`) resolving to this path — set at write time, stable thereafter, never a direct UNC path (NFR-16); **(3) `<item_slug>/<doc_type_slug>/staged/<original_filename>`** — `[D-039]` Step 3 ambiguous new-vs-revision holding (item resolved but `doc_id_slug` assignment pending); surfaced as `Document classification ambiguous` flag on PM dashboard; on PM resolution HILDA assigns to an existing `<doc_id_slug>/revN/` or creates a new `<doc_id_slug>/rev1/`; **(4) `<item_slug>/outbound/`** — HILDA-generated artifacts only (QC reports, diagnostics, submission-review outputs); never owner deliverables; never written to PLM or carrier portal. **Zip file handling**: zip files are audit-only — stored in `_zip_audit/`; never uploaded to PLM or carrier portal; version tree operates on individual files only (zip-level versioning is irrelevant). PLM receives extracted individual files as **flat attachments** (PLM is an issue tracker — no directory structure; each extracted file becomes one attachment with its `original_filename`; per-TG collision risk on duplicate filenames acknowledged per `[D-054]`). Carrier portal receives extracted individual files with **source-folder hierarchy preserved** per FR-77 Type-2 routing — the matched source folder + any sub-tree under it is preserved on the carrier side. **PLM and carrier portal content thus differ structurally for zip-extracted files**: PLM is flat; carrier is hierarchical. PLM-source zips remain on PLM unchanged (HILDA never modifies PLM); HILDA extracts locally for routing + carrier upload, writing extracts to NSD1 classified tree for audit consistency. **NSD classified path (`<item_slug>/<doc_type_slug>/<doc_id_slug>/revN/`) is the source of truth for in-progress owner deliverables; PLM is source of truth for submitted deliverables only** (after OwnerClosed + TPM approval; anchors `[D-040]`); PLM issues created per FR-26. **Ingest write flows by source** — PLM upload timing is **phase-conditional** for Email/NSD/TPM-via-FR-62 sources and uploads only individual files (never zips): **Ph-1** — immediate (single revision per document; `rev1 = is_final = true` auto-set); **Ph-2** — deferred until `OwnerClosed` + TPM approval; only the `is_final = true` revision is uploaded; deferred upload fires post-dispatch via FR-68 sync verification (anchors `[D-040]`, `[D-041]`). PLM-polled documents already in PLM, never re-uploaded; FR-68 handles post-dispatch PLM↔NSD and PLM↔Carrier hash sync verification: for **Email**, HILDA classifies via FR-52 — if attachment is a ZIP, extracts to `_zip_audit/` then routes each extracted file via FR-52; otherwise routes the individual file via FR-52, uploads individual files to owner's PLM issue, records `(delivery_item_id, plm_id, doc_type, doc_id_slug, rev_number, plm_attachment_id, upload_timestamp, ingest_source, local_classified_path, original_filename, file_hash, first_page_excerpt, is_final, download_url, parser_result, llm_review_findings, from_zip, source_zip_filename)` in the HILDA document index (`ingest_source` enum: `Email`, `CorporatePLM`, `NetworkSharedDrive`, `SharePointUI`), writes document to `<item_slug>/<doc_type_slug>/<doc_id_slug>/revN/`; for **PLM poll**, document already in PLM — if attachment is a ZIP, extracts locally to `_zip_audit/`; HILDA applies FR-52 routing + D-039 classification, records `plm_attachment_id` and `local_classified_path`, writes extracted individual files to `<item_slug>/<doc_type_slug>/<doc_id_slug>/revN/` (no PLM re-upload); for **NSD drop** (NSD1 or NSD2), HILDA detects per FR-55 — if file is a ZIP, extracts to NSD1 `_zip_audit/`; routes individual files via FR-52 (folder path is one signal among many, not authoritative); uploads individual files to PLM, writes to NSD1 classified path. Items with `no_customer_upload = true` (FR-80) skip BOTH PLM upload AND carrier portal upload. All download links HILDA-mediated (`https://hilda.corp/dl/<scoped_token>`) — never direct UNC paths (NFR-16); `actual_item_info` holds the PLM issue URL for the (owner × milestone) pair per FR-57.
- **FR-55** `[Ph-1]` — For DeliveryItems whose `tracking_modality includes NetworkSharedDrive`, HILDA polls **both NSD1 (`\\NSD1\<carrier>\<device>\<milestone>\<Folder-N>\`) and NSD2 (`\\NSD2\<carrier>\<device>\<milestone>\<Folder-N>\`)** per the dual-NSD topology in FR-13 (anchors `[D-013]` impl note 2026-05-28). When a new file is detected, **item routing uses the full FR-52 5-step pipeline** — folder path is one signal among many (consulted at step 3 if the TG has `folder_routing_enabled = True`), NOT the authoritative item identifier as in the prior per-item-folder model. The file is recorded in `CommunicationLog` with `ingest_source = NetworkSharedDrive` (filesystem identity attribution deferred to Ph-3 — see DEF-16). **Zip files**: extracted recursively to `_zip_audit/`; each extracted file routed via FR-52. **doc_type**: derived from resolved item's `item_type` per the 1:1 mapping (no separate classification — see FR-7 / `[D-053]`). HILDA uploads each individual file (never zips) to the owner's PLM issue per FR-13's phase-conditional rule (**Ph-1**: immediate; **Ph-2**: deferred until `OwnerClosed` + TPM approval, only `is_final = true` revision uploaded per `[D-040]`) + FR-80 `no_customer_upload` gating, writes the document file to `<item_slug>/<doc_type_slug>/<doc_id_slug>/revN/` in the NSD1 internal tree, updates the HILDA document index, updates the DeliveryItem record in SharePoint and sets `actual_item_info` to the PLM issue URL (per FR-57) on first document arrival for this item. ### Latency & reliability

- **NFR-9** — DeliveryItem state changes propagate from owner action to PM dashboard within one poll interval + processing time; webhook / push is preferred and delivers within 60 s; for polled channels (Email FR-23, PLM FR-26, NSD FR-55), propagation latency equals the effective deadline-tiered `polling_schedule` interval at the time of the action — far from deadline the interval is longer (acceptable; no active submission pressure); near the deadline (≤ 1 day tier) the interval is 5–15 min target; the 60 s guarantee applies only to webhook/push-delivered events. **Architecture design notes — must address during architecture phase:**
  1. **Async LLM tasks** — FR-52 tier-2, FR-12 path(c), FR-53, FR-54 must execute as Celery background tasks and must never block a state-change event; the state transition (DocumentReceived, OwnerStatusConfirmed) fires and propagates within the polling-interval SLA; the LLM result (AIReviewResult) arrives as a subsequent async event and updates the PM dashboard independently; architecture must enforce this decoupling at the task-dispatch boundary.
  2. **Submission assembly progress** — FR-18 package assembly (NSD download + carrier upload) is minutes-scale for large milestones, not sub-60 s; SP UI must show immediate "in progress" feedback on Submit to Carrier click; progress granularity = per-file (`files_done / total_files × 100`, split across download phase and upload phase); progress state written to Redis by the Celery task; HILDA API exposes `GET /milestone/{id}/submission/progress`; SP web part polls at 5 s intervals until completion; individual document downloads (FR-61) stream directly from NSD with `Content-Length` set — browser handles per-file progress natively; bulk document download (Ph-2+) uses async ZIP assembly + dashboard notification with one-time download link.
  3. **Polling channel latency** — Email (FR-23), PLM (FR-26), NSD (FR-55) share a single `polling_schedule` AutomationRule; the effective interval for a milestone is the shortest tier applicable across any of its active items; polling ceases per FR-74 collection phase closure; propagation latency from owner action to PM dashboard is bounded by the effective tier interval — not a flat fixed value.
- **NFR-10** — All external service calls — Email (FR-23), PLM/IssueTracker (FR-25/FR-26), NSD SMB (FR-13/FR-55), corp messenger (FR-50), CustomerJIRA (FR-25), on-prem LLM (hilda-llm-gateway / FR-53), SharePoint REST (NFR-8), and carrier portal adapter (FR-18/FR-19) — must never fail silently; every failure produces a registered error code per `[D-002]` and routes per FR-75; retry policy by failure class: **(a) Transient** (network timeout, 5xx, service momentarily down) — exponential backoff with jitter: base 30 s, max 30 min, max 5 retries; after max retries exhausted raise error code and route per FR-75; **(b) Rate-limited** (429/throttled) — respect `Retry-After` header if present; otherwise same exponential backoff as (a); **(c) Auth failure — transient** (AD/Kerberos unreachable) — exponential backoff as per (a); **(d) Non-recoverable** (400, 404, data corruption, permanent 403) — no retry; raise registered error code immediately; Email Service polls or receives 24/7; polling interval for Email, PLM, and NSD is deadline-tiered per the shared `polling_schedule` AutomationRule (FR-23, FR-26, FR-55); auth credential failures route per NFR-11.
- **NFR-11** — When a PM credential is expired or missing, the dependent automation step is queued (not lost) and the PM is alerted via the dashboard and an out-of-band channel; the queue-and-alert pattern (step queued, not lost, human alerted) generalises to all failure classes requiring human resolution: **(a) PM credential expired/missing** — step queued, PM alerted (this NFR); **(b) document classification permanently ambiguous** (`staged/` hold per FR-52) — item remains `DocumentReceived`, PM flagged on dashboard for manual resolution; **(c) on-prem LLM gateway down** — FR-53 review tasks queued, `HildaOpsAlert` fired; items with `review_required = true` and `review_status = pending` remain blocked at `OwnerClosed` guard condition (2) until LLM recovers — TPM may unblock by setting `review_required = false` via FR-14; **(d) version-selection timeout** `[Ph-2 FR-66]` — after configurable max-retry corp messenger attempts without owner response, PM dashboard flag for manual version override via FR-14; **(e) FR-68 PLM sync loop non-convergence** — after configurable max-retry cap, PM dashboard flag + `HildaOpsAlert`; **(f) Celery beat missed schedules on restart** — beat resumes from current time; missed fires not replayed; acceptable for reminder/escalation rules (next scheduled fire covers it); time-critical one-shot events must be Celery tasks, not beat schedules.

### Task idempotency & recovery

- **NFR-20** — All Celery tasks are idempotent — re-executing a task after a worker crash, Redis restart, or network partition must produce the same result as executing it once; requirements: **(a) `acks_late = True`** on all tasks — broker re-queues the task before acknowledgement so a worker crash cannot silently drop an in-flight task; **(b) all external writes check "already done"** before acting using a stable natural key: PLM issue creation checks `plm_id` already set on the DeliveryItem; SP List updates check current `delivery_state` before overwriting; document index writes use `(delivery_item_id, doc_type, doc_id_slug, rev_number)` as the natural key; email sends check `CommunicationLog` for a matching `(batch_id, action_type)` entry; **(c) Redis AOF persistence required** — without append-only file persistence the Celery broker queue is lost on Redis crash, causing all in-flight tasks to be silently dropped; AOF must be enabled on the Redis container in the Docker Compose configuration; **(d) all retry attempts emit a registered `WFL-W` warning code** per `[D-002]` so retry storms are visible in Prometheus dashboards (per `[D-023]`) and do not accumulate silently.

### Version selection, PLM sync, and portal structure

- **FR-66** `[Ph-2]` — When the `OwnerClosed` transition fires (FR-7 / FR-28) and multiple revisions exist for any `doc_id_slug` under a DeliveryItem, HILDA triggers the corp messenger version-selection workflow as the transient fork from `OwnerClosed`: HILDA sends the owner a corp messenger message listing all revisions for the conflicting `doc_id_slug(s)` (rev number, `original_filename`, upload timestamp) and asks the owner to select the final version; the owner's reply (by revision number or filename) is parsed and the selected revision's `is_final` flag is set to `true` in the document index; all other revisions for that `doc_id_slug` have `is_final` set to `false`; after all version selections are confirmed, the DeliveryItem advances from `OwnerClosed` (transient) to `UnderPMReview`; if the owner does not respond within a configurable timeout, the PM is notified on the dashboard and the item remains in `OwnerClosed` transient hold pending resolution; TPM may manually set `is_final` directly from the `UnderPMReview` SP UI (FR-56) as an override path; `[Ph-1]` only `rev1` exists per document — `is_final = true` is auto-set for rev1 of each document and the item advances directly to `UnderPMReview` without any owner selection step.

- **FR-67** `[Ph-2]` — When HILDA's post-dispatch deferred PLM upload (triggered by FR-18 dispatch → `SubmittedToCustomer`) uploads the `is_final` revision to PLM and detects that a stale attachment for the same `doc_id_slug` already exists in the PLM issue, HILDA initiates PLM stale file deletion; stale attachments arise in two scenarios: **(a) re-submission** — a prior dispatch deferred-uploaded an earlier `is_final` revision (e.g. `rev2`); TPM subsequently uploaded `rev3` via FR-62, re-approved and re-dispatched; the current deferred upload uploads `rev3` and `rev2` is now stale; **(b) CorporatePLM modality** — the owner uploaded the document directly to PLM; HILDA's deferred upload of the `is_final` revision creates a duplicate — the owner's original PLM attachment is stale; in both cases HILDA sends the owner a corp messenger message listing the stale attachment(s) and requests confirmation of deletion; upon owner confirmation, HILDA calls `deleteAttachment` on the IssueTracker adapter for each stale attachment and records the deletion in `CommunicationLog`; **`deleteAttachment` failure** — if `deleteAttachment` returns an error (e.g. HILDA's service account is not the file owner and lacks delete permission on the PLM system), the failure is flagged on the PM dashboard via FR-56 as `PLM stale attachment — delete failed: <filename>` and also logged to `HildaOpsAlert` (FR-75); this flag is visible to TPM regardless of the item's `delivery_state`; TPM must manually delete the stale attachment directly in PLM; **timeout** — if the owner does not confirm within a configurable timeout, the PM is notified and the item is flagged on the PM dashboard for manual resolution; `deleteAttachment` is a new operation added to the `IssueTracker` Protocol (see `[D-008]`) surfacing the PLM system's native attachment-delete capability.

- **FR-68** `[Ph-1]` — After a milestone's submission package is dispatched to the customer portal (FR-18), HILDA runs **two sync verification loops** for each DeliveryItem in the milestone: **(A) PLM-NSD sync** (existing): `[Ph-1]` HILDA polls the owner's PLM issue to verify that `rev1` (the single revision in Ph-1; `is_final = true` auto-set) is present in PLM as a current attachment; if not present, HILDA uploads `rev1` from the NSD classified path to PLM via the IssueTracker adapter and re-verifies; `[Ph-2]` approved revision is the `is_final = true` revision selected via FR-66; if not present in PLM, HILDA uploads the approved revision from NSD and re-verifies; if stale attachments (non-final revisions) remain in PLM, FR-67 stale deletion is triggered. **(B) PLM-Carrier hash sync** (anchors `[D-054]`): for every individual file uploaded to the carrier portal, HILDA recomputes `file_hash` and verifies that hash exists in PLM — either as a top-level attachment OR as a member of a zip attachment on PLM (extracted+hashed at verification time); non-match emits `ITR-W003 — PLM-Carrier hash mismatch on file '{filename}' item '{item_id}'`; PM dashboard surfaces for manual reconciliation. **Both phases**: verification result (pass / fail / pending) is written to `CommunicationLog` and surfaced on the PM dashboard. Both verification loops run as Celery tasks per `(milestone_id, hilda_dispatch_run_id)` at a configurable interval and stop when all items are verified or a maximum retry count is reached. Items with `no_customer_upload = true` are excluded from FR-68 sync entirely (no PLM or carrier upload occurred to verify).

- **FR-69** `[Ph-1]` — Each customer's carrier portal submission structure is defined in `customizations/<customer_slug>/portal_structure.yaml`; this file is authored by PM team leads at customer onboarding and loaded by the customer adapter at assembly time (FR-18); the `portal_structure.yaml` schema is defined in `core/src/customer_adapter/MODULE.md`; the file lives in `customizations/` (customer-specific, not in `core/`) and is never read by the dev LLM directly; changes to portal structure require updating this file only — no code change in `core/`; the schema includes: **(a) folder / hierarchy layout** — carrier-side folder path or issue-field mappings per `doc_type` (e.g., Google Drive subfolder names, Jira attachment fields, FTP directory paths); **(b) `file_overwrite_policy: overwrite | rename`** — `overwrite` for carriers where uploading a file with an existing name replaces it (some Google Drive configs, SFTP with replace semantics); `rename` for carriers where previously uploaded files cannot be deleted or replaced (Jira attachments, most FTP sites, custom portals) — HILDA uploads the revised file with a distinct name derived from `revision_file_suffix_pattern`; **(c) `revision_file_suffix_pattern`** — used only when `file_overwrite_policy = rename`; a pattern applied to `original_filename` to produce the carrier-side filename for revised submissions; supports `{N}` (revision number) and `{timestamp}` (ISO date) tokens — e.g., `_rev{N}` yields `testreport_rev2.pdf`; `_{timestamp}` yields `testreport_20260519.pdf`; the `original_filename` in the HILDA document index is never modified — only the carrier-upload filename is affected.

- **FR-70** `[Ph-1]` — Each DeliveryItem has an `item_completion_pct` computed field (0–100 integer) representing progress towards document delivery and review completion. **`[Ph-1]` formula (document review progress):** `(count of test_report doc_id_slugs for this item whose rev1 row has non-null llm_review_findings) / doc_count × 100`; `doc_count` (from the template, per FR-7) is the denominator — it represents the expected number of test reports and is fixed at tracker creation; example: `doc_count = 3`, two test reports received and reviewed → `item_completion_pct = 67`; all three received and reviewed → `item_completion_pct = 100`; supplementary documents (`tech_report`, `waiver`) do not contribute to `item_completion_pct` — they are outside the `doc_count` definition. **`[Ph-2]` formula (test-case pass rate):** `(count of test cases whose status ≠ failed across the latest revision of all received test reports for this item) / (total test cases across the latest revision of all received test reports for this item) × 100` — numerator includes all non-failed outcomes (passed, non-applicable, not-supported, waived, and any other non-failed status value); if no test reports have been received, `item_completion_pct = 0`; this formula uses the parser result data produced by FR-16 and reflects actual test-case outcomes rather than document-review completion. **`Confirmation` items:** `item_completion_pct = 100` when `delivery_state ∈ {OwnerClosed, UnderPMReview, ReadyForSubmission, SubmittedToCustomer, Closed}`; `item_completion_pct = 0` before `OwnerClosed` (no documents expected — completion is signalled by owner confirmation). `item_completion_pct` is recomputed on every new document index write (new `doc_id_slug`, new revision, or new `llm_review_findings` write) and on every `delivery_state` change for `Confirmation` items. The field is persisted on the `DeliveryItem` SharePoint List row and is available in the milestone view (FR-56) for PM monitoring. Milestone-level `milestone_completion_pct` (FR-6) is the average of its child DeliveryItems' `item_completion_pct` values.

### Owner Discovery

- **FR-71** `[Ph-2]` — The Owner Discovery Function (ODF) fires automatically at tracker creation for each unique `tg_name` group in the milestone **where `email_group_alias` is not set**; TGs with `email_group_alias` set are self-organizing — ODF is suppressed entirely for those TGs; `owner` field overrides by TPM (FR-14) are stored for PLM and NSD purposes but are not applied to email outreach for alias-enabled TGs; for non-alias TGs: ODF sends one corp messenger message per TG group to that TG's `tg_owner` (pre-populated from the customer template per `tg_name` at tracker creation per FR-2; TPM may override `tg_owner` per TG group in the SP UI before ODF fires); the message lists all items in the TG grouped by their currently assigned `owner`, showing each distinct owner's corp ID / email and their associated items; when any item in the TG has `tg_owner == owner`, the message explicitly notes this and asks the TG owner to confirm they will submit those deliverables themselves; **response format** — two valid reply types, matched case-insensitively: (a) `confirmed` — no changes; all current item owners in this TG stand as-is (including any items where `tg_owner == owner`); (b) one or more `old_corp_id → new_corp_id` lines — for each line, HILDA reassigns all items in **this TG only** currently owned by `old_corp_id` to `new_corp_id`; an engineer does not work across TGs so reassignment scope is always within the TG group; matching accepts both corp ID and full email, case-insensitive; multiple reassignment lines are processed independently; **after parsing response:** HILDA updates the `owner` field on all affected DeliveryItems, records each change in `CommunicationLog` with the TG owner's corp ID and the old→new mapping, and notifies PM with a per-TG change summary; a flag is surfaced on the PM dashboard for any TG where `tg_owner == owner` for at least one item — informational only, not a blocker; the TG owner is a fully valid delivery engineer for those items and participates in the normal outreach and document-tracking flow; **timeout:** if `tg_owner` does not respond within a configurable period, PM is flagged on the dashboard; tracker proceeds with template default owners; **SP UI:** the milestone view (FR-56) displays ODF status per TG group before Start Collection — `Confirmed`, `Updated (N engineers reassigned)`, `Timed out — using defaults`, or `Pending`; TPM may proceed with Start Collection regardless of ODF status; inbound ODF response parsing uses the corp messenger inbound infrastructure per FR-54.

### ZIP Ingestion

- **FR-72** `[Ph-2]` — **ZIP receipt and storage:** when a `.zip` file is received via any ingest channel (Email, NSD1, NSD2, PLM-source), HILDA stores the raw archive as an **audit-only artifact** in the NSD1 internal tree at `\\NSD1\internal\<carrier>\<device>\<milestone>\<tg_name_slug>\_zip_audit\<original_zip_filename>.zip`, co-located with its extracted contents at `_zip_audit/<original_zip_filename>/<extracted-tree>/` (anchors `[D-050]` impl note 2026-05-28). `original_zip_filename` is preserved as received. **ZIP files are never uploaded to PLM or carrier portal** — they exist purely as HILDA-side audit/provenance artifacts (anchors `[D-054]`). For PLM-source zips, the zip stays on PLM unchanged (HILDA never modifies PLM); HILDA extracts locally for routing + carrier upload + classified-tree write for audit consistency. **Extraction:** HILDA extracts all files from the ZIP recursively (nested zips are extracted in turn until no zips remain); for quality review purposes (FR-53), the following file types are eligible for AI review: `.xlsx`, `.xlsm`, `.xls`, `.pdf`, `.doc`, `.docx`, `.ppt`, `.pptx`; files of other types are stored and submitted to the carrier portal as-is but are not passed to the AI review pipeline — logged and added to the `HildaOpsAlert` queue as an informational note; there is no restriction on file type for carrier portal submission — every individual file extracted from a ZIP is submitted regardless of type. **Routing extracted files:** each extracted file is individually processed via FR-52's 5-step routing pipeline as if it arrived as a standalone attachment; every document produced from ZIP extraction records two additional fields in the HILDA document index: `from_zip: true` and `source_zip_filename: <original_zip_filename>` (ZIP filename as received from owner); extracted files are written to `<tg_name_slug>/<item_slug>/<doc_type_slug>/<doc_id_slug>/revN/` in the NSD1 internal tree per FR-13; for files that fall to D-039 Step 2 (LLM new-vs-revision classification), Ph-2 LLM resolves. **Version tree on individual files only** — zip-level versioning is irrelevant; `[D-039]` + `[D-048]` apply per extracted individual file; multiple zips containing files with overlapping names are processed independently. **Same-filename detection across ZIPs:** if a file within an incoming ZIP has an `original_filename` matching an existing document index entry for the same `(delivery_item_id, doc_type)`, HILDA emits `EML-W006 — duplicate filename '{filename}' across zips '{zip_a}' '{zip_b}' in TG '{tg}'; manual triage` for PM/TPM review; treatment is per D-039 pipeline in FR-52 (hash match → duplicate; slug match → revision; LLM-ambiguous → staged). **Unresolved routing:** if any extracted file cannot be routed to a DeliveryItem via FR-52's first four steps, it lands at FR-52 step 5 (staged → associated with milestone's default work-item per FR-78); `DocumentIndexRow.unrouted_source_path` captures the originating context (e.g., `<zip_filename>/<nested-folder-path>`); TPM resolves per FR-83. The ZIP archive remains in `_zip_audit/` regardless of whether all, some, or no files are successfully routed. All background processing faults (extraction errors, classification failures) route to `HildaOpsAlert` per FR-75; fine-grain routing to distinct TPM/support-team destinations is deferred: DEF-21. **Carrier submission**: only individual extracted files are submitted to the carrier portal (per FR-18 + FR-77 — zip files are never uploaded); `from_zip: true` documents follow the same FR-77 Type-2 routing as standalone files. **TG3-style fixed zip-internal folder structure**: TGs whose zips have fixed routable folder names (`folder_routing_enabled = True`) use the outermost folder name inside the zip as input to FR-52 step 3 source-folder template; see FR-52.

### Submission Package Download

- **FR-73** `[Ph-1]` — The SP milestone view (FR-56) surfaces a **Download Package** action available to PM and TPM; enabled when all DeliveryItems in the milestone are in `ReadyForSubmission` or `SubmittedToCustomer` state and at least one item is in `ReadyForSubmission` — identical guard to FR-63. The assembled file is named `<carrier_slug>_<device_slug>_<milestone_slug>_package.zip`. Assembly failure is shown in the SP milestone view as UI feedback (PM-triggered action — result always surfaced in UI) and also logged to `HildaOpsAlert` for support team investigation (FR-75; DEF-21).

  **Two-click async flow**:
  - **(i) Click 1 — request**: PM/TPM clicks **Download Package** action in SP milestone view → button is wired to modify an SP list field per FR-84 (e.g., set `download_package_request_timestamp = NOW()`) → SP fires alert email → HILDA's `email_service` consumes via IMAP IDLE / short-poll → `sp_alert_parser` extracts the action verb + field deltas → dispatches `download_package` Celery task to `hilda-worker` (per `[D-021]` / `[D-022]`). SP UI immediately updates the same row to show "Package preparing..." status (replaces the Download Package button with a progress indicator).
  - **(ii) Async assembly** (`hilda-worker`, no user interaction): the Celery task iterates qualifying items per the Package content selection rule below, reads individual files from NSD1 classified path, constructs the folder hierarchy per FR-77 Type-2 routing, creates the `.zip` archive with internal folder structure replicating the carrier portal layout, and stores the zip at a HILDA-PC temporary cache with a scoped download token. **Per-click regeneration**: each click of Download Package triggers a fresh assembly; previous cached zip is discarded; ensures fresh milestone state on every download (no caching across clicks).
  - **(iii) Completion write-back**: when assembly completes, HILDA writes back to SP via SP REST API + NTLM/Kerberos per `[D-006]` (outbound is always allowed) — updates SP list fields on the milestone row: `download_package_url = https://hilda.corp/dl/<scoped_token>`, `download_package_status = "ready"`, `download_package_generated_at = NOW()`.
  - **(iv) SP UI detects completion**: SP web part polls the HILDA status endpoint at 10s intervals per FR-56 soft refresh until task completes; when `download_package_status = "ready"` is observed, the web part replaces the "Preparing..." indicator with a clickable **Download Now** link (which is the `download_package_url`).
  - **(v) Click 2 — download**: PM/TPM clicks **Download Now** link → browser navigates to the scoped URL (routed through IT-admin's corp-side reverse proxy per FR-84) → HILDA's download endpoint authenticates the requestor via on-prem AD per NFR-16 → endpoint serves the cached `.zip` with `Content-Disposition: attachment` per FR-61 → browser downloads to the TPM's Downloads folder.
  - **(vi) Cache lifecycle**: the cached `.zip` is **deleted immediately after successful download** (file streamed to browser → deleted on stream completion); FR-76 `MilestoneStorageCleanup` provides a backstop for any cached zips that never completed download (e.g., TPM never clicked the link).
  - **(vii) Post-download** (no SP interaction): TPM manually extracts the `.zip` via Windows Explorer's "Extract All", 7-Zip, or any archive tool → folder hierarchy unfolds on local PC matching the carrier portal layout. The browser does not perform extraction — it only delivers the `.zip` to the TPM's Downloads folder; TPM-side extraction is a manual step.

  **Package mirrors FR-18 carrier-portal submission** (anchors `[D-053]`, `[D-054]`): individual files only (NO audit zips); folder structure per FR-77 Type-2 routing — matches the carrier portal target layout exactly. The zip's **internal folder hierarchy replicates the carrier portal layout** — `<target_folder>/<matched_source_folder>/<subtree>/<filename>` exactly as it is/would be on the carrier portal. **Package content selection** — scoped to `ReadyForSubmission` items where `item_type ≠ Confirmation` AND `no_customer_upload = false`: `[Ph-1]` all individual files at NSD1 classified path `<tg_name_slug>/<item_slug>/<doc_type_slug>/<doc_id_slug>/rev1/`; `[Ph-2]` individual files where `is_final = true` only — same selection rule as FR-18. **Excluded**: audit zips from `_zip_audit/` (PM accesses individual zip archives via FR-57 download endpoint if direct audit needed); default work-item documents (per FR-78 no-upload condition). **No state change** — downloaded package is for PM review and pre-submission verification only; state advancement and carrier portal submission remain exclusively via FR-63 / FR-18.


### Collection Phase Closure
- **FR-74** `[Ph-1]` — **Collection phase closure:** HILDA evaluates the milestone's collection status after every DeliveryItem state change; collection is considered closed when all DeliveryItems **except the default work-item** (FR-78) in the milestone are in `{ReadyForSubmission, SubmittedToCustomer, Closed}` — the default work-item is excluded from this threshold check because it never reaches `ReadyForSubmission`/`SubmittedToCustomer` (no carrier submission per FR-78); the default work-item's terminal state (`Closed`) is reached separately via the TPM-Mark-Closed path on the default work-item itself once all its associated documents are resolved (see FR-78); items in `Blocked` or `Delayed` state keep collection open — polling remains active for those items until they also reach the threshold. **On threshold crossing — final sweep:** before halting, HILDA performs one final sweep across all ingest channels for the milestone: (a) **NSD** — one final poll of all `inbound/` folders for the milestone's items; (b) **PLM** — one final poll of all PLM issues for the milestone; (c) **Email** — any queued or unprocessed emails for the milestone's `BATCH-<id>` are processed to completion; all files detected in the final sweep are ingested via normal flows (FR-52, FR-55, FR-26, FR-72). **Polling halt:** after the final sweep completes, all polling for the milestone stops — FR-26 PLM polling, FR-55 NSD monitoring, and FR-25 CustomerJIRA polling all cease; inbound emails for the milestone's `BATCH-<id>` are silently ignored after the final sweep; any NSD drops or PLM uploads after this point are not processed and generate no owner notification; ignored inbound activity is recorded in `CommunicationLog` with `action_type: IgnoredPostClosure` for audit purposes only. **Closure is permanent:** collection closure does not reverse even if a DeliveryItem reverts below `ReadyForSubmission` (e.g. FR-62 upload on a `SubmittedToCustomer` item reverts it to `UnderPMReview`); SP UI (FR-62) is the only accepted upload channel after closure; TPM is responsible for all further document uploads.

### Milestone Storage Cleanup

- **FR-76** `[Ph-1]` — **Milestone storage cleanup on all-items-Closed:** HILDA monitors the `Closed` state transition on every DeliveryItem; when all DeliveryItems in a milestone reach `Closed` state (via FR-14 per-item override, FR-64 bulk Close All Items, or FR-7/FR-80 TPM-Mark-Closed for `no_customer_upload` items), HILDA triggers a permanent storage cleanup for that milestone. **Cleanup scope** (anchors `[D-013]` + `[D-050]` impl notes 2026-05-28): **(a) NSD1 internal tree** — the full milestone subtree `\\NSD1\internal\<carrier>\<device>\<milestone>\` is deleted, including all TG group folders (`<tg_name_slug>/_zip_audit/`, classified `<item>/<doc_type>/<doc_id_slug>/revN/`, staged `<item>/<doc_type>/staged/`, outbound `<item>/outbound/`); **(b) HILDA PC local cache** — temporary files downloaded during submission assembly (FR-18) or package download (FR-73) for this milestone are deleted. **NOT deleted**: **(c) NSD1 owner-inbound flat folder** (`\\NSD1\<carrier>\<device>\<milestone>\<Folder-N>\`) — preserved; owners may continue dropping documents post-closure (HILDA ignores them per FR-74 collection halt + `CommunicationLog action_type: IgnoredPostClosure`, but the folder itself stays); **(d) NSD2** — never touched by HILDA per `[D-013]` impl note 2026-05-28 (NSD2 is read-only from HILDA's perspective; originals stay forever, no archival). Document download links (FR-61) will return 404 after cleanup — download any needed documents before proceeding. Only close items after the carrier has confirmed technical acceptance of the milestone submission."*; advisory only — does not block the close action.

### Fault Handling

- **FR-75** `[Ph-1]` — **Fault routing principle:** all faults and processing errors in HILDA route as follows: **(a) PM-triggered actions** — any SP UI button click (Start Collection, Submit to Carrier, Download Package, Approve, Upload, etc.) always surfaces its result (success or failure) in the SP UI to the PM immediately on completion; the same result is also logged to the `HildaOpsAlert` queue for support team investigation; **(b) background processing faults** — faults arising from background jobs (ZIP extraction errors, document routing failures, classification failures, polling errors, email processing errors) route to `HildaOpsAlert` only; no PM notification is generated for background faults; in Ph-1 and Ph-2 all faults — regardless of type — are routed to a single `HildaOpsAlert` queue; fine-grain routing to distinct support-team vs TPM/PM-dashboard destinations is deferred to Ph-3 (DEF-21); cited by FR-72, FR-73.

### Customer portal routing, default work-item, per-item flags

- **FR-77** `[Ph-1]` — **Document → Customer portal target-folder routing (Type-2 pipeline).** Once a document is routed to a work-item via FR-52, HILDA determines the carrier portal upload destination via a 2-step pipeline: (1) **Folder-based** (TG opt-in via `folder_routing_enabled=True`): outermost source folder (NSD or zip-internal) substring-matched against TG's `folder_routing.yaml` entries; if matched, entry's `target_folder` (full carrier-side path) used; (2) **Work-item fallback**: if folder routing didn't fire OR TG has no folder routing template, use `work_item_routing` section keyed by resolved work-item-id → `target_folder`. **Upload destination**: `<carrier>/<target_folder>/<matched_source_folder>/<subtree>/<filename>` where `<target_folder>` is full carrier path from template (may be nested), `<matched_source_folder>` is outermost source folder name preserved verbatim (including any noise like `audio(done)`), `<subtree>` is everything below the matched source folder preserved as-is. Step 2 (no source folder context) produces `<carrier>/<target_folder>/<filename>`. **No-upload condition**: documents associated only with default work-item (FR-78) cannot be uploaded — TPM must resolve to real work-item via FR-83. Template structure at `customizations/template_schemas/<customer_slug>/folder_routing.yaml`:
  ```yaml
  <tg-name>:
    folder_routing:
      <source-folder-substring>:
        work_item: <work-item-id>            # for FR-52 step 3 (optional)
        target_folder: <full-carrier-path>   # for FR-77 step 1 (optional)
    work_item_routing:
      <work-item-id>: <full-carrier-path>    # for FR-77 step 2 fallback
  ```
  **Template-incomplete failure case** — work-item resolved but no `work_item_routing` entry exists for it (template gap; ops hasn't mapped this work-item to a carrier target folder): HILDA raises `EML-W007 — target folder not mapped for work-item '{id}'; manual triage required` and surfaces on PM/TPM dashboard. Document is held in NSD classified path; carrier portal upload is suppressed until ops updates the customer's `folder_routing.yaml` to add the missing `work_item_routing` entry. PLM upload still fires per the standard path (PLM is unaffected by carrier-target-folder mapping).

  **FR-69 portal_structure.yaml retained** for carrier mechanics (overwrite policy, suffix patterns) applied at dispatch time after FR-77 path determination. Two YAMLs with distinct concerns. Anchors `[D-053]`.

- **FR-78** `[Ph-1]` — **Default work-item per milestone (auto-instantiated).** Every milestone instantiated by HILDA at tracker creation includes an auto-instantiated default work-item as the milestone's last DeliveryItem (`sort_order = max+1`; not editable; cannot be deleted). Default work-item: `item_type = Default`; belongs to system-reserved TG named `"_unrouted"`; `doc_count = 0`; `review_required = false` (cannot be set true); accepts documents of any of the 5 `doc_type` values per FR-86 (classification per FR-85 still runs at ingest for downstream FR-83 reassignment quality; `[D-039]` revision determination is SKIPPED at ingest when routing lands on Default — deferred to FR-83 reassignment time per FR-86 storage matrix); does NOT participate in carrier submission — files associated only with default work-item cannot be uploaded to carrier portal per FR-77; **does NOT gate `ReadyForSubmission` of other items** in the milestone — other items proceed to submission independently; **does NOT count toward FR-74 collection-phase-closure threshold** (default work-item is excluded from the `{ReadyForSubmission, SubmittedToCustomer, Closed}` check); **DOES gate full milestone closure** (the `MilestoneAllClosed` trigger per FR-28 + `MilestoneStorageCleanup` action per FR-29) — the default work-item must reach `Closed` before milestone-wide cleanup fires. **How default work-item reaches `Closed`**: once all its associated documents have been resolved (reassigned to real work-items via FR-83 or accepted as legacy per FR-83's TPM workflow), TPM clicks **Mark Closed** on the default work-item row in SP UI; HILDA enforces the guard *"no remaining documents associated with this default work-item via `DocumentItemAssociation`"* at click time → default work-item advances to `Closed`. **Template structure** under `default_work_item:` block per milestone:
  ```yaml
  <milestone-name>:
    default_work_item:
      item_name: "Unrouted Documents"          # optional; default if absent
      item_description: ""                      # tags not applicable (no routing)
      owner: null                               # optional; default null
      expected_completion_date_offset_days: 0   # optional; defaults to milestone.target_date
  ```
  **Template fallback**: if the customer template does not define a `default_work_item:` block for a milestone, HILDA auto-instantiates with system defaults: `item_name = "Unrouted Documents"`, `item_description = ""`, `owner = null`, `expected_completion_date = milestone.target_date`. Documents failing FR-52 routing (step 5) associated via multi-item table (FR-79); `DocumentIndexRow.unrouted_source_path` captures originating context (NSD parent path or zip-internal path). Documents remain associated until TPM resolves them via FR-83. Anchors `[D-053]`.

- **FR-79** `[Ph-1]` — **Multi-item document association.** One document may be associated with multiple work-items (e.g., a test report covering test cases for items I-1 and I-2). HILDA represents via M:M join table `DocumentItemAssociation(document_index_row_id, delivery_item_id, association_kind: Literal["primary", "secondary"])` in Postgres (storage module). Every document has **exactly one** entry with `association_kind = 'primary'` (matching `DocumentIndexRow.delivery_item_id` per FR-57) and **zero-or-more** entries with `association_kind = 'secondary'`. The duplication of the primary association across `DocumentIndexRow` and `DocumentItemAssociation` is intentional — it supports single-query lookup of "documents for item X" without a UNION across both tables. **When multi-item association fires**: FR-52 step 1 (strict substring on tags) — if the same filename satisfies the tag-set of multiple items, all matched items receive an association entry. Highest-tag-count match → `primary`; others → `secondary`. **SP UI rendering** (FR-56): primary items display the document with a download link; secondary items display a reference link pointing to the primary item's row. **PLM upload — fan-out across distinct owners**: each item has exactly one owner; multiple items in the same TG may share an owner or have different owners. The file is uploaded **once per distinct `(owner × milestone)` PLM issue** in the multi-item association set: if all matched items share the same owner, the file lands in that owner's single PLM issue (one upload); if matched items have N distinct owners, the file is uploaded N times, one per owner's PLM issue (each upload carries the same `file_hash` per FR-68 hash sync invariant). This ensures every owner whose item(s) the document touches sees the file in their respective PLM issue. The `DocumentItemAssociation` table per-association `plm_attachment_id` field records the per-PLM-upload attachment IDs (one row per (item, plm_issue) pair). **Carrier portal upload**: file uploaded once per FR-77; primary item's target-folder resolution wins (single file on carrier portal regardless of multi-item association). Anchors `[D-053]`.

## Appendix A — Rule Engine: Triggers, Conditions, and Actions

All rules fire via `AutomationRules` evaluated by the rule engine (FR-28 – FR-31). Column definitions: **Trigger** = event type from the FR-28 taxonomy; **Condition** = guard that must hold for the rule to fire; **Actions** = FR-29 action verbs invoked; **State Transition** = resulting `delivery_state` change on the target DeliveryItem; **Ph** = earliest phase in which the trigger/action is active; **FR refs** = authoritative requirements.

> **Note — Start Collection (FR-8):** PM/TPM clicking **Start Collection** in the SharePoint UI (FR-56) is a direct HILDA request, not a rule engine trigger. It creates PLM issues per (owner × milestone), calls `SendInitialOutreach` for all open items, and advances all to `OutreachSent`. For items added after Start Collection has already fired, `ItemCreated` mid-collection fires `StartItemCollection` instead (row 2).

> **Note — StateChange (row 6):** `StateChange` fires on any `delivery_state` transition and is an observation point for downstream rules. It does not independently initiate state transitions and has no default action — rules scoped to it are customer-configurable.

### A.3 Delivery state machine

Valid `delivery_state` transitions per DeliveryItem:

```
Open
 └─[Start Collection / StartItemCollection]──────────────────────► OutreachSent
                                                                         │
                              ┌──────────────────────────────────────────┤
                              │ OwnerStatusConfirmed "done"               │ AttachmentReceived;
                              │ (Confirmation item only)                  │ doc_count reached
                              │                                           ▼
                              │                                   DocumentReceived
                              │                                           │
                              │                                           │ AIReviewResult
                              │                                           │ (no state change — updates
                              │                                           │  llm_review_findings only)
                              │                                           │
                              │                           OwnerStatusConfirmed "done"
                              │                           (both conditions met: doc_count
                              │                            reached AND (review_required=false
                              │                            OR all docs reviewed))
                              │                                           │
                              ▼                                           ▼
                         OwnerClosed ◄─────────────────────────── OwnerClosed
                         (transient)                               (transient)
                              │
                    ┌─────────┴────────────────────────┐
                    │ [Ph-1] single rev per doc         │ [Ph-2] multiple revisions
                    │ is_final=true auto-set            │ for any doc_id_slug
                    ▼                                   ▼
             UnderPMReview ◄────── FR-66 version selection ──── (owner selects via
             (TPM review gate)      (corp messenger)              corp messenger)

Delayed  ◄──[OwnerStatusConfirmed "delayed"; any pre-approval state]
Blocked  ◄──[OwnerStatusConfirmed "blocked"; any pre-approval state]
Delayed / Blocked ──[PM or owner reversal]──► (prior active state)

UnderPMReview ──[PMApproval — TPM approves in SP UI]─────────────► ReadyForSubmission   [Ph-1]
ReadyForSubmission ──[Submit to Carrier (FR-63)]─────────────────► SubmittedToCustomer  [Ph-1]
SubmittedToCustomer ──[FR-14 per-item or FR-64 bulk manual override]► Closed               (automated FR-22 deferred: DEF-20)
```

**Guards:**
- `Confirmation` items (`item_type = Confirmation`): skip `DocumentReceived` and `UnderPMReview`; `OwnerStatusConfirmed "done"` from `OutreachSent` is valid; `OwnerClosed` transient → `UnderPMReview` immediately (no documents, no `is_final` fork needed).
- All other item types: `OwnerStatusConfirmed "done"` from `OutreachSent` is **not** valid — triggers `NotifyPM` (`Premature closure attempt`) instead.
- `CustomerJIRA` items: reach `OwnerClosed` via HILDA detecting JIRA closure; no owner message required; transient fork applies normally.
- `Delayed` and `Blocked` are transient overlay states — the item re-enters its prior active state when the PM or owner reverses.
- `AIReviewResult` does **not** produce a state transition — it updates `llm_review_findings` in the document index and notifies the PM, satisfying the `OwnerClosed` guard condition (2) when all revisions are reviewed (`review_required = true` items only). When `review_required = false` on an item, guard condition (2) is vacuously satisfied — no `AIReviewResult` is awaited and the item advances to `OwnerClosed` immediately once condition (1) is met and the owner confirms "done".
- `Closed` is reachable via FR-14 manual per-item `delivery_state` override or FR-64 bulk Close All Items action; automated transition via FR-22 is deferred (DEF-20); Milestone → `Complete` when all items are `Closed`.

### C.3 Non-functional requirements (all phases)

NFRs are architectural invariants active from Phase 1 onward. None are phase-gated.

| NFR | Area | Summary |
|-----|------|---------|
| **NFR-1** | Data boundary | All HILDA services on-prem; no cloud or SaaS LLM calls |
| **NFR-2** | Data boundary | Compact reports / logs leaving on-prem contain no proprietary content |
| **NFR-3** | Credential security | Per-PM isolation; Ph-1/Ph-2 secrets store = sops `.env` files per `[D-038]`; Vault / centralised secrets service deferred to Ph-3 (DEF-14) |
| **NFR-4** | Credential security | Ph-1/Ph-2: sops AES-256-GCM at rest, startup-time decrypt into process memory; TLS in transit; per-request decrypt + pod isolation + mTLS deferred to Ph-3 (DEF-14) |
| **NFR-5** | PM approval | No customer-facing outbound without explicit PM-approval signal recorded in `CommunicationLog` |
| **NFR-6** | PM accountability | Every external action attributable to a specific PM; `CommunicationLog` append-only |
| **NFR-7** | SharePoint | Deployment-specific SP values in `customizations/sharepoint_config/` only; none in `core/` |
| **NFR-8** | SharePoint | SharePoint REST API + on-prem AD auth (NTLM / Kerberos) against SP 2017; List CRUD + classic web parts only |
| **NFR-9** | Latency | Webhook/push: < 60 s; polled channels: within deadline-tiered poll interval (baseline configurable; ≤1-day tier: 5–15 min target); LLM tasks async (never block state transition); submission assembly progress tracked per-file via Redis |
| **NFR-10** | Reliability | All external service calls never silent-fail; retry tiers: (a) transient → exponential backoff base 30 s / max 30 min / 5 retries; (b) rate-limited → respect Retry-After; (c) non-recoverable → no retry, raise code immediately; auth failures route per NFR-11 |
| **NFR-11** | Reliability | Queue-and-alert pattern for all human-resolution failures: credential (step queued + PM alerted); staged doc (PM dashboard); LLM down (tasks queued + HildaOpsAlert); version-selection timeout (PM dashboard); FR-68 non-convergence (PM dashboard + HildaOpsAlert); beat missed schedules (resume from current time) |
| **NFR-12** | Adapter / build boundary | Dev LLM has no access to proprietary API specs, template schemas, or historical test reports |
| **NFR-13** | Adapter / build boundary | Generated proprietary artifacts under `customizations/` only; `core/` contains Protocols, Ingestors, public-vendor adapters |
| **NFR-14** | Extensibility | New item types, modalities, states extensible via configuration; no schema migrations |
| **NFR-15** | High availability | `restart: unless-stopped` in Docker Compose (Ph-1/Ph-2); HA replicas and MicroK8s deferred to Ph-3 (see `[D-043]`) |
| **NFR-16** | NSD boundary | NSD reads via HILDA-mediated download endpoint only; on-prem AD authentication required; direct UNC paths never exposed; per-DeliveryItem ACL deferred (DEF-18) |
| **NFR-17** | Chat-mediated collaboration | All module RPT / MET / FIX / QC reports contain only counts, flags, bounded enum tokens — no proprietary content |
| **NFR-18** | Chat-mediated collaboration | All failures raise registered error codes from central `error_codes.py` in format `{MODULE}-{E\|W}{NNN}` |
| **NFR-19** | Test interface | Every side-effect module ships `--mock` / `--dry-run`; every UI module ships mock web harness without production SP access |
| **NFR-20** | Task idempotency | All Celery tasks: `acks_late=True`; all external writes check "already done" via natural key; Redis AOF persistence required; all retries emit `WFL-W` warning code |
